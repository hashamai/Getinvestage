## Problem Statement
Build a portfolio project that gets its author hired (hired-first, learn-by-building second). The vehicle is a stock-market assistant: Phase 1 is a clean, deployed dashboard on top of yfinance; later phases add AI features (data analysis, RAG, chatbot). Tech stack: Python + FastAPI backend, React frontend. The core risk is generic-ness: yfinance dashboards and "RAG chatbot over stock data" are among the most common portfolio projects, so the plan optimizes for a sharp, memorable point of view over feature count.

## What Makes This Cool
The differentiator (chosen by the builder): **an AI that is actually useful and grounded** — it answers real questions with citations, not a wrapped ChatGPT. The headline feature is a **RAG-powered equity research assistant**: it retrieves from a genuinely rich text corpus (news articles, earnings-call transcripts, SEC filings, analyst commentary) and answers questions like "What's the sentiment on Tesla?" or "Summarize NVDA's last earnings call" with inline source citations. Underneath, lightweight **tool-calling** handles structured/numeric questions ("what's the P/E", "how did my watchlist do this week") by fetching real numbers from the backend instead of hallucinating them. RAG stays the star; tool-calling is the safety net that keeps it from embarrassing itself on math. That hybrid — RAG for text, tools for numbers — is exactly the judgment senior engineers look for, and most portfolio projects get it wrong.

## Constraints
- Solo developer, portfolio timeframe (weeks, not months).
- Stack fixed: Python/FastAPI + React.
- Must be deployed and clickable — the live URL is the single most important artifact.
- Cost-sensitive: free/cheap data sources (yfinance, free news API tiers) and a cost-controlled LLM budget.
- Windows dev environment.

## Premises
1. **The AI is the star; the dashboard is the supporting cast.** Build the dashboard clean, but it exists to feed the AI data and give its answers somewhere to point. Agreed.
2. **RAG stays central on the resume/project, paired with tool-calling as a safety net.** Builder chose to keep RAG the headline (over a pure tool-calling reframe). Resolution: make the RAG corpus genuinely rich (news + transcripts + filings) so RAG does real, impressive work over unstructured text; add lightweight tool-calling so numeric questions get correct answers. Best of both. Agreed (adjusted).
3. **Deploy on day one, not at the end.** Every phase ships to a live URL. Agreed.
4. **Phase 1 ships as a complete, polished, deployed vertical slice before any AI.** Agreed.

## Approaches Considered
### Approach A: Thin slice, ship weekly (RECOMMENDED, sequenced toward B)
Ship the smallest useful deployed version each week, each slice aimed at Approach B's full RAG-assistant vision. Effort M, Risk Low. Live from day one; every week the demo link is better; nothing is ever half-built. Downside: early versions look modest; may need one refactor as architecture emerges.

### Approach B: Full phased build
Phase 1 polished dashboard (deployed), Phase 2 full RAG assistant with tool-calling + citations + eval set, Phase 3 extras. Effort L, Risk Med. Most impressive finish and widest range signal; downside is longer time before the AI (the star) is live and higher stall risk.

### Approach C: AI-first niche ("AI Earnings-Call Analyst")
Drop the general dashboard; build one sharp thing extremely well. Effort M, Risk Med. Sharpest point of view, smallest surface to polish; downside is narrower breadth signal, and everything rides on the AI being good.

## Recommended Approach
**Approach A sequenced toward B's end state.** Ship thin deployed slices weekly so the live URL exists immediately (hired-first), but aim each slice at B's full vision (RAG assistant with citations + a small eval set). Gets A's low risk with B's impressive finish. Keep C's "niche it hard" instinct in reserve if the general dashboard starts to feel generic — you can always narrow the framing to "AI equity research analyst" without changing the architecture.

## Architecture (target end state)
- **Backend (FastAPI):**
  - `market` service: Finnhub client (see Engineering Review Decisions) with a persistent cache + serve-stale-on-error. Endpoints: quote, history, fundamentals, search.
  - `news` service: pulls articles/headlines per ticker (free tier: e.g. a news API or RSS). Feeds the RAG corpus.
  - `rag` service: ingestion (chunk + embed text into a vector store), retrieval, and answer synthesis with citations. Start with a local vector store (Chroma or FAISS) to keep it free; SQLite/pgvector later.
  - `assistant` endpoint: an LLM agent with (a) tools that call the `market` service for structured/numeric questions and (b) a `search_docs` tool that hits the `rag` service for text questions. The LLM decides which to use.
  - `portfolio`/`watchlist`: simple persisted list (SQLite) so "how did my watchlist do this week" works.
- **Frontend (React):**
  - Dashboard: ticker search, price + chart, key fundamentals, watchlist. Handle loading / empty / error states explicitly.
  - Assistant: chat panel with streamed responses and clickable citations that link back to the source article/transcript.
- **Infra:** backend as a container/web service, frontend as a static build. LLM calls behind a server-side key with a hard budget cap and response caching.

## Engineering Review Decisions (2026-07-02, /plan-eng-review)
- **Market data source: Finnhub free tier as PRIMARY** (60 calls/min, real-time quotes + fundamentals + company news), with a persistent cache layer (SQLite/Redis, generous TTL, serve-stale-on-error). yfinance dropped as primary — it's a scraper with no SLA and cloud host IPs get blocked, which would break the live demo (the #1 hiring artifact). Alpha Vantage rejected (free tier now ~25 calls/day).
- **Deploy target: Render (FastAPI) + Vercel (React).** Both free, GitHub auto-deploy. Finnhub key stays a server-side env var on Render (never in the React bundle). CORS scoped to the Vercel domain.
- **RAG corpus: deferred to Slice 3.** Do NOT decide news/filings/transcripts now — focus on Slices 0-1. When at Slice 3, lead with Finnhub company news + SEC EDGAR filings (both free + legal); earnings-call transcripts are NOT in scope (no clean free/legal source).
- **Auth: none for the demo** (single shared watchlist) unless multi-user becomes a deliberate signal later.

## Open Questions (deferred — decide at the relevant slice)
- **Slice 2-3: LLM + embeddings provider/budget.** Latest capable model with a hard monthly cap; cheap/open embedding model. Must include per-IP rate limiting + a budget cap before the assistant endpoint goes public (a public LLM endpoint on your key = anyone can drain your budget).
- **Slice 2-3: agent routing.** How the assistant decides tool-call vs RAG. Start with simple/explicit function-calling before a full agent loop — reliable routing is where these projects fail.
- **Slice 3: RAG corpus finalization** (news + SEC EDGAR, per decision above).

## Slice 0-1 Engineering Detail (near-term, focused scope)
```
FastAPI backend (Render)                         React SPA (Vercel)
  services/market.py                               TickerView (search -> price + chart)
    get_quote / get_history / search               Watchlist (add/remove, persisted)
    -> Finnhub client (+ cache, stale-on-error)    loading / empty / error states
  api/routes.py                                     calls backend via VITE_API_URL
    GET /quote/{ticker}  200/404/503              CORS: allow Vercel domain only
    GET /history/{ticker}
    watchlist add/remove/list (SQLite)           Secrets: FINNHUB_API_KEY = Render env var
  startup: fail fast if FINNHUB_API_KEY missing
  CI: GitHub Actions -> tests -> auto-deploy
```

### Test requirements (write alongside code, not deferred)
- `market.py`: cache hit; cache miss -> fetch -> cache; bad ticker -> 404; Finnhub 429/5xx/timeout -> serve stale or 503; empty/invalid input -> 422. (mock the Finnhub HTTP client)
- `routes.py`: /quote 200/404/503; /history happy + failure; watchlist add, duplicate-add, remove-missing.
- Frontend: loading/empty/error render states; **[E2E]** search valid ticker -> price+chart renders; invalid ticker -> clear error (not blank); backend-down -> error state (not infinite spinner).

### Failure modes (handle + test, or flag as critical silent-failure gap)
| Failure | Test? | Error handling | User sees |
|---|---|---|---|
| Finnhub 429 rate limit | required | serve stale cache or 503 | last-good data or clear "try again" |
| FINNHUB_API_KEY missing on Render | required | fail fast at startup, clear log | n/a (caught before deploy) |
| CORS misconfigured | required (real domain) | correct allow-origin | data loads instead of silent block |
| Provider timeout | required | timeout + stale fallback | last-good data, not hang |

- Slice 5 "wow extra" (risk view / alerts) — optional, only after 0-4 are polished and live.

## Success Criteria
- A live URL a recruiter can open and use in under 30 seconds without setup.
- The assistant answers a numeric question correctly (via tool-calling) and a text question with a working citation link (via RAG) — both demoable in the README with GIFs.
- A short **eval set** (10-20 Q&A pairs) the assistant is measured against, with results in the README. This is the senior-level signal most portfolios lack.
- README leads with: one-line pitch, live link, 30-second demo GIF, architecture diagram, and the "why RAG for text + tools for numbers" design note.
- Clean, tested backend services (at least the `market` cache and the assistant routing logic have tests).

## Distribution Plan
Web service — the "distribution" is the deployed URL plus the GitHub repo. CI/CD: GitHub Actions to run tests on push and auto-deploy backend + frontend on merge to main. Set this up in Phase 1 so every later phase ships live automatically.

## Next Steps (build order — thin weekly slices)
1. **Slice 0 (day one): deploy skeleton.** FastAPI "hello" + one real endpoint (`/quote/{ticker}` via Finnhub), React app that displays one ticker's price, both deployed (Render + Vercel) with CI. Key as Render env var, CORS to Vercel domain. Live URL exists. This is the foundation everything else lands on.
2. **Slice 1: real dashboard.** Ticker search, price chart (history endpoint), key fundamentals, a persisted watchlist. Handle loading/empty/error states. Make it look genuinely good — this is the frame the AI sits in.
3. **Slice 2: numeric assistant (tool-calling first).** Add the `assistant` endpoint with tools that call your `market` service. Ship a chat panel that correctly answers "what's AAPL's P/E" and "how did my watchlist do this week" from real data. This proves grounding before RAG.
4. **Slice 3: RAG over news (the headline).** Build `news` ingestion → chunk/embed → vector store → `search_docs` tool. Assistant now answers "what's the sentiment on Tesla / why did NVDA move" with clickable citations. This is your resume centerpiece.
5. **Slice 4: enrich the corpus + eval.** Add earnings-call transcripts and/or filings to the RAG corpus. Build the eval set and put results in the README. Depth signal.
6. **Slice 5 (optional): one wow extra.** Portfolio risk/correlation view, price alerts, or "explain this chart" — pick one, only after 0-4 are polished and live.
